## Workshop scope and environment

- **Use LAB.md as the contract.** Build the small HTTP/ESQL weather integration, with projects in `projects/`, BARs in `output/`, and runtime data in `.workdir/`. The public path is `/weather/current`, without an added API prefix. Invalid coordinates return JSON HTTP 400; upstream failures return appropriate non-2xx JSON errors. Do not add MQ, SOAP, audit persistence, shared infrastructure, JavaCompute, or DEV/QA/UAT/PROD files solely because the generic rules mention them. Keep applicable configuration, error-handling, and testing practices.
- **Resolve the original skill name to the installed skills.** The original `ace-bob` guidance is provided here as `ace-project-setup`, `ace-message-flow`, `ace-esql`, and `ace-subflow`. Activate the relevant skills and read their references before implementing artifacts. The mode adds the `skill` tool group for this. Do not claim to activate a nonexistent `ace-bob` skill.
- **Respect source-only work.** If ACE is absent or the user requests source preparation only, generate and statically review files without installing software, building, or deploying. Report generated, statically checked, built, deployed, and runtime-tested separately. Mark unperformed checks as not run. Neither XML parsing, an AI review, nor this repository's `npm test` proves that a generated ACE project compiles or runs. Existing projects and server configuration belong to the participant; preserve them.
- **Use actual installed tools.** Do not assume the original examples' SoapUI projects, service libraries, or absolute paths exist. On Windows, initialize ACE with `call "<actual-path>\mqsiprofile.cmd"` in the same `cmd.exe` process as each ACE command. Adapt to the actual OS. Verify command help, listener ports, and TLS settings before building or deploying; do not copy `curl -k`/`-sk`, disable certificate checks, change security policies, or expose an unauthenticated admin listener. Run `node test-api.mjs` only against an actual deployed ACE integration. Also check upstream failures and timeouts; those are not covered by the supplied script.

## Clarifications to the original technical guidance

- **Compute mode:** its default is **Message**, not `destinationAndMessage` as some original examples state. When changing the local environment, explicitly select LocalEnvironment and Message (`computeMode="destinationAndMessage"`), preserve `InputLocalEnvironment` in `OutputLocalEnvironment`, and then set overrides. Use the input/output-specific correlation names in Compute ESQL. [Compute documentation](https://www.ibm.com/docs/en/app-connect/13.0.x?topic=nodes-compute-node).
- **HTTPRequest terminals:** follow rule file 7: `out`, `error`, and `failure`. The `timeout` terminal listed in file 2 does not exist on HTTPRequest; transport timeouts use Failure. Configure a finite `timeoutForServer`, explicitly select GET, and handle HTTP errors separately from transport failures. Do not assume every failure has an HTTP status or JSON body. [HTTPRequest documentation](https://www.ibm.com/docs/en/app-connect/13.0.x?topic=nodes-httprequest-node).
- **Use an ordinary Application with plain HTTP nodes.** For this lab, use HTTPInput → Compute → HTTPRequest → Compute → HTTPReply, plus validation and error paths. Include `.project` and `application.descriptor`, not a specialized REST API project, `restapi.descriptor`, or generated REST dispatch. Set HTTPInput `parseQueryString="true"` and read `InputLocalEnvironment.HTTP.Input.QueryString`, not `InputLocalEnvironment.REST.Input.Parameters`. Keep the endpoint exactly `/weather/current`.
- **Use the default broker schema.** Keep `.msgflow` and `.esql` files at the `WeatherAPI` Application root and omit `BROKER SCHEMA`. This is the root-level convention in file 7, overriding file 3's blanket requirement for a schema declaration. Each Compute node must reference its actual, uniquely named ESQL module using `computeExpression="esql://routine/#ModuleName.Main"`; do not introduce `gen/` or a named schema for this exercise.
- **Validation and ESQL:** a nonnumeric CAST can throw rather than return NULL; use the documented DEFAULT form or a scoped handler to return the required 400. ESQL PROPAGATE uses logical names such as `'out1'`, not XML names such as `'OutTerminal.out1'`, and explicit propagation should not also trigger a default reply. Verify that error paths set the actual HTTP status and a JSON body. [CAST](https://www.ibm.com/docs/en/app-connect/13.0.x?topic=functions-cast-function) · [PROPAGATE](https://www.ibm.com/docs/en/app-connect/13.0.x?topic=statements-propagate-statement).

Original examples are guidance, not a guarantee of correctness. If other details conflict with installed ACE schemas or authoritative IBM documentation, verify and explain the discrepancy rather than silently guessing.
